# Hana Desk Pet：独立 Hana App 与 macOS 桌宠

更新时间：2026-10-17。当前实现基线为原生桌宠 **0.5.7**、控制台 **0.6.4**、本机协议/schema **v3**。产品方向已从“让 Hana 驱动已安装 CrossPet”改为**Hana v2 管理 App + 独立 macOS 原生桌宠端**。这里的桌宠不属于 CrossPet，也不是 Hana 卡片里的宠物。

## 产品边界

- **Hana App 管理层：** 订阅公开会话事件，按 `app/sessions.read` 授权读取标题/Agent；维护最近活动会话快照、手动宠物选择和连接开关；只发布脱敏 DTO。
- **macOS 宠物端：** 独立原生 App，自行渲染角色与动作；桌面默认只见角色本体，不显示状态/会话文字或控制面板；提供仅绑定 loopback 的本机 API；宠物本地手动改选后由 Hana App 轮询并回写选择。
- **不做：** 适配/驱动已安装 CrossPet、写 CrossPet 状态/用户配置、Hana 卡片内宠物、Windows 首版、模型/用量权限（用量以后若需单独加 `app/usage.read`）、系统安装或登录项。

## 桌面显示硬约束

默认桌面只显示原创角色本体与动作；角色外完全透明。禁止矩形/玻璃底板、边框、品牌、常驻状态/会话文字、选角/退出按钮或悬浮控制面板。会话和连接配置留在 Hana 控制台；角色与窗口位置操作通过角色右键原生菜单。此约束是验收标准，不是视觉建议。

## 公开 SDK 可行性核验

核验本机 Hana v2 1.1.7-beta `APPS.md`、随包 `@hana/app-sdk` types 与 `hana-app-creator` 技能。

### 可用的 App 主动回环出口

公开 `sdk.network.fetch(url, init?)` 是**由 Hana 宿主代理执行的受控出站 HTTP**。App 在 manifest 声明 `network`，host/method/localhost/超时/响应大小在调用时由宿主校验。要访问本机 HTTP，需把 `127.0.0.1` 写入 `allowedHosts` 并显式设 `allowLocalhost: true`；`network` 配置不是单独的 capability 名，但新增 host/localhost 权限走 App Manager 既有审查。`network.fetch` 从 Hana App 后端调用，不依赖 UI 页私有凭据。

建议首版声明：

```json
"network": {
  "allowedHosts": ["127.0.0.1"],
  "methods": ["GET", "POST"],
  "allowLocalhost": true,
  "defaultTimeoutMs": 1200,
  "maxResponseBytes": 16384
}
```

`allowedHosts` 是主机白名单，不包含端口约束；权限审查展示主机名单，但不逐项展开端口、`allowLocalhost` 或方法。因此代码固定宠物端口，不接受可由会话/用户输入的任意 URL，并把该网络声明视为需要用户审查的本机权限。桌宠端仅绑定 `127.0.0.1`；宿主端点不可用、协议标识错误或请求失败时停止同步，不回退到其它接口。通过合成测试可验证客户端 DTO，但在 App 未安装/批准前不能声称宿主代理实际连接已实测。

### 为何不用 Hana 托管服务 / App routes / App-owned window

- `ctx.runtime.start({ service })` 需要 `app/runtime.execute`，注册的是 Hana 管理的回环服务；公开契约只承诺通过 `/api/apps/<appId>/routes/_runtime/<runtimeId>/` 受管代理访问。浏览器 service URL 带短期 AppSurface 路径票据。
- `ctx.runtime.fetch(runtimeId, ...)` 的 origin 固定为该 App 自己已注册且 ready 的服务，仅供 App 主入口调用；它不给独立原生客户端新权限。**契约没有承诺该 service port 可由外部桌面进程直接发现/连接，因此不假定直连。**
- `ctx.routes` 的 App routes 受 `app_route` 鉴权：宿主 owner 登录态或该 App 的 surface session。没有公开 SDK 给任意原生宠物签发/获取可复用的 owner 或 surface 凭据；不复用、搬运 Hana 私有 token。
- `ctx.bus.handle` / `sdk.publicData` 是 Hana App 间的服务/数据共享机制，不是任意 macOS 进程 API。`sdk.appEvents.emit` 是 Hana 桌面 App 内事件通道，不是面向任意 OS 进程广播。
- `sdk.windows` / `app/windows.manage` 只提供普通 App-owned 原生窗口创建/控制（show/focus/minimize/maximize/fullscreen 等）；公开类型没有 always-on-top、透明、鼠标穿透或宠物窗口 level 控制。不用普通 Hana 窗口冒充独立桌宠。

### 最小 capability 与授权

- `app/sessions.read`：读取其它归属会话的标题/Agent 元数据；未授予时 UI 使用 session ID 稳定回退。
- `network` manifest 白名单：给 Hana App 到 `127.0.0.1` 的受控出站权限；无独立 `app/network.fetch` capability。
- **不申请** `app/runtime.execute` / `.native` / `.local-machine`、`app/windows.manage`、`app/services.*`、`app/public-data.*`、`app/usage.read`。宠物是独立构建目标，不是 Hana App 子进程。

## 本机协议草案

宠物端固定绑定 `127.0.0.1:43127`，端口冲突时 fail closed。Hana App 是唯一 HTTP 客户端；宠物不会访问 Hana API。Bridge 在 App UI 中显式启用且默认关闭，服务健康检查确认 `{ service: "hana-desktop-pet", protocolVersion: 1 }` 后再发送活动数据。

| 方法/路由 | 方向 | 允许用途 |
|---|---|---|
| `GET /v1/hello` | Hana → Pet | 健康检查、协议版本/服务标识 |
| `POST /v1/snapshot` | Hana → Pet | 角色目录与脱敏活动状态；角色选择通过独立 selection 路由同步 |
| `GET /v1/selection` | Hana → Pet | 读取宠物本机菜单的角色选择及 revision；App 轮询并持久化 |
| `POST /v1/selection` | Hana → Pet | 将 Hana UI 的手动选择回写；携带 `expectedRevision`，冲突回传当前值 |

`POST /v1/snapshot` 的 envelope 为 `{schemaVersion,revision,characters:[{id,name}],activity:{sessionId,title,agentId,agentName,status,toolName,lastActivityAt}}`；选择路由使用 `{schemaVersion,characterId,revision,updatedAt}`（读取）或 `{schemaVersion,characterId,expectedRevision,updatedAt}`（写入）。服务端/客户端严格限制方法、路径、JSON key、枚举、字符串长度、请求体大小与状态码；不接受未知字段。Hana event 先经 `state-core` 白名单处理，不发送原始 event、聊天正文、args、result、sessionPath 或密钥。

“回写”是逻辑双向、HTTP 始终由 Hana 发起：Pet 本机选角更新自己的状态/revision，Hana 通过固定 `GET /v1/selection` 观察并写入 `sdk.storage.global`；Hana 页面改选则用带期望 revision 的 `POST` 写回 Pet。冲突按更新时间/revision 显示并收敛，事件从不参与角色选择。

## 威胁模型与限制

按罐头指定的单用户本机桌面：只绑定 IPv4 loopback，Bridge 显式开关，字段白名单，绝不传聊天正文；不加 Ed25519/X25519/AES-GCM/人工指纹核验。Loopback 不是进程身份认证，固定端口存在抢占/同用户进程冒充风险；宿主 manifest 也不限制端口。健康标记只防误连与协议错配，不是密码学身份认证。本原型不承诺抵御同用户恶意程序、键盘/屏幕监控或已失陷系统；若威胁模型扩大，再重新做安全设计，而不是把当前协议称作抗恶意本机进程。

普通活动会话标题仍是私人元数据。未安装/审批 App 前只用合成数据；真实运行必须由用户在 App Manager 审查 `app/sessions.read` 与 localhost 网络声明。

### 系统命中与避让边界

- `PetWindowView.hitTest` 仍只决定**本进程内**视图命中。跨应用避让另由主线程 30 Hz Timer 读取 `NSEvent.mouseLocation`，经 `window.convertPoint(fromScreen:)` 转换后调用相同角色几何，再切换公开 `NSWindow.ignoresMouseEvents`：角色外整窗忽略鼠标，系统可把事件交给底层 App；按下到 mouseUp/取消期间和根菜单/子菜单 tracking 期间保持接收。失去 window 与退出时恢复 `ignoresMouseEvents=false`。锁定位置不影响点按/右键。
- 这是整窗开关轮询，不是逐像素 WindowServer 输入形状，也不是首击零竞态。30 Hz 的名义采样间隔约 33 ms：指针快速进入角色时首击可能仍穿透到下面应用；离开时上一次接收状态也可能短暂保留。每秒约 30 次主线程几何命中计算，成本未实测。没有事件 tap/global monitor、私有 CGS API 或新增权限。
- 合成测试验证事件策略（拖拽、嵌套菜单、失窗重置）与运动变换（最大耳尖/鲸顶/闪光/尾部保守边界、正逆变换）；NSBezierPath 实际光栅边缘、WindowServer 时序、跨 Space/全屏及 VoiceOver 实际导航仍未启动 GUI 验证。

## 会话绑定与列表标题修复（控制台 0.5.0）

只改 Hana App，不动 Swift/`.app`/素材。

### 标题解析

`buildSnapshot` 原先只给 `current` 挂 `displayTitle`，`sessions` 数组没有该字段，面板 `renderSessions` 的 `item.displayTitle ?? item.title` 于是取到空值，退化成裸「会话」。现在 `buildSnapshot` 用 `attachTitles(rows)` 把同一套 `displayTitleFor` 应用到每一行；`projectSessionList` 也对清单条目做同样处理。解析顺序不变：有标题→同标题加 Agent 名→短 ID 兜底为「会话 · 短ID」，不因修显示而放宽隐私投影。

### 跟随决策

`resolveFollow(follow, { sessions, listEntries, listAvailable, now })` 是纯函数，返回 `{ follow, view }`：

- `mode: "latest"`（默认）→ `view` 取 `latestActive(sessions)`；`latestActive` 跳过 `isClosedSession()` 为真的会话，但没有任何其它候选时仍回退到它，避免关闭最后一个会话时 `current` 变空。
- `mode: "pinned"` → `view` 恒为被钉 ID。释放条件：事件流里该会话已真正关闭（`isClosedSession()`）；或清单里 `lifecycle !== "active"`；或清单可读且该 ID 缺席超过 `PIN_MISSING_GRACE_MS`。释放时写入 `released: { sessionId, reason, at }`（`pinned_closed` / `pinned_archived` / `pinned_missing`）。`listAvailable === false` 时不计缺席，避免把「读不到清单」误判成「会话已消失」。

### 什么算「已关闭」（控制台 0.6.3）

宿主会对用户仍在使用的会话发 `session_closed`（关闭后继续对话），旧实现把 `closedAt` 当成永久的关闭标记，于是点下去固定、同一次 `refreshFollow` 就被释放。现在的规则分两层：

1. **写入层**：`applyEvent` 收到属于该会话的活动事件（`agent_start` / `turn_start` / `auto_retry_start` / `tool_execution_start` / `tool_execution_end` / `agent_end`）时把 `closedAt` 清零；`session_created` / `session_forked` 这类 idle 事件不算活动，不清零。`runEnded` 语义未动（关闭后紧接的孤立工具事件仍被 terminal-run 守卫丢弃）。
2. **判定层**：`isClosedSession(record)` = `closedAt > 0 && closedAt >= lastActivityAt`。`latestActive`、`selectCurrent`、`resolveFollow` 都走这一个函数，所以即使旧存储里残留着「关闭后又活动」的记录，也不会被当成关闭。

两处防线是有意的冗余：单改写入层会让旧数据继续误判，单改判定层会让记录本身的语义失真。

面板侧的列表补充逻辑同样改用 `closedAt > 0 && closedAt >= lastActivityAt`，保持前后端判定一致。`released` 的提示文案改为「已自动解除固定「X」：…」，因为释放永远是控制台自动判定，不是用户点了取消。

`rebuildSnapshot(snapshot, follow, now)` 让 `current` 在没有事件的情况下也能跟随钉住/解钉变化。

### 存储与隐私

- `hana-pet.session-list`：`{ schemaVersion, observedAt, available, sessions[] }`，条目只含 sessionId / title / agentId / agentName / lifecycle / displayTitle。加载时用 `projectSessionList` 重新投影，外部写入不被信任。
- `hana-pet.follow`：mode / pinnedSessionId / updatedAt / followedSessionId / reason / missingSince / released。`released` 带 `FOLLOW_NOTICE_TTL_MS`，过期后不再保留（临时 UI 上下文而非持久状态）。
- `hana-pet.follow.request`：面板单向请求键，带 `requestId` 去重；`index.js` 校验会话 ID 形状（`/^[A-Za-z0-9_.:@-]{1,256}$/`）后才生效，非法值直接忽略。用独立请求键而不是直接写 `hana-pet.follow`，是为了让自动释放不会被面板的旧值重新套用。

## 会话身份归属、诊断与下拉稳定性（控制台 0.5.2）

实机证据：`hana-pet.activity.snapshot` 里有 5 条 `local-session-1..5`（title/agentName 全 null），其中 `local-session-3` 是 `working/exec_command/0 秒前`；而用户正在对话的 `sess_0mvbpagcf_…` 是 `idle/1119 秒前`。同快照另有 20 多条正常 `sess_*`，说明标题解析本身没坏。同时 `session-list` 停在 13 分钟前的 `available: false`。

### 根因

`resolveIdentity` 的兜底：

```js
const sessionId = declaredId ?? cleanId(session?.sessionId) ?? cached?.sessionId ??
  (path ? `local-session-${++fallbackSequence}` : null);
```

事件只带 `sessionPath`、`session:get` 又解析不出 ID 时，这条路径每进程新造一个 id。真实会话的活动于是全记到不存在的会话上，真实会话的 `lastActivityAt` 再不更新 → 永远看起来空闲。`local-session-N` 还会在重启后重新从 1 开始，旧行变成不可归并的垃圾。

### 修法

- **路径 → id 映射**：`resolvedPaths: Map<path, {sessionId,title,agentId,agentName}>`。来源是 `session:list` 条目的 `path` + `sessionId`（`AppSessionListEntryV2` 自带 `path`）与成功的 `session:get`。只在内存，路径不入库、不外发。
- **稳定占位键**：解析不出来时用 `unresolvedKeyFor(path)` = `unresolved:` + FNV-1a(path) 的 8 位十六进制。同一路径跨事件、跨多次调用恒定，不再每事件一个新 id；散列单向，不嵌入路径原文。
- **归并**：`mergeSnapshot(snapshot, fromId, toId, now, identity)` 把占位行的 status/running/toolName/closedAt/`lastActivityAt`/`statusAt` 搬到真实行并删除占位行；identity 只取宿主给的 title/agentId/agentName，绝不从占位行借。重建时 `current` 由真实 id 产生。
- **占位不可冒充**：`cleanSession` 从 id 派生 `unresolved`（不信任外部字段）。`latestActive` 跳过占位；`buildSnapshot` 对最终 target 再判一次，占位一律降为 `null`。`normalizeFollow`/`isPinnableSessionId` 拒绝对占位下钉；`projectSessionList` 不把占位放进可选清单；`displayTitleFor` 对占位固定输出「未识别会话 · 短ID」。
- **旧行清理**：`recoverSnapshot` 丢弃 `isPlaceholderSessionId` 的行。路径从不持久化，加载后的占位永远无法归并，保留只会继续堆积。

### 诊断

`sessionDiagnostic(error, {operation})` 只保留三个字段：`code`（`/^[A-Z0-9_.]{2,64}$/`）、`kind`（限定 permission/timeout/aborted/unsupported/host/empty/malformed/ok）、`operation`（`/^[a-z:.]{2,48}$/`）。`AppSdkError` 本来就把 message 与原 error 分开，这里再取一次白名单，等于双重保险。落 `hana-pet.session-diagnostics`，`list`/`get` 两个槽位；成功时清空该槽。面板把 `kind` 译成中文原因并附上原始 `code`。

### 下拉稳定性

每 1 秒的 `render()` 会走到 `renderFollowOptions()`。原实现对 `replaceChildren` 全量重建并无条件写 `value`，下拉展开时被反复重建，既闪又跟用户选择打架。现在：

1. 先比较内容签名（`跟随最近活动` + 每项 `[sessionId, displayTitle]` 的 JSON），相同直接返回。
2. 签名变化时若下拉被聚焦或已展开（`mousedown`/`focus` 置位，`blur`/`Escape`/`Enter` 清除），只把新签名记到 `followSelectDeferred`，不重建。
3. 关闭时补做一次重建。
4. `value` 只在确实不等于目标值时赋值。

## 诊断提示分流（控制台 0.5.3）

### 问题

0.5.2 的 `renderSessionDiagnostics`：

```js
const failure = diagnostics?.list ?? diagnostics?.get ?? null;
...
nodes.sessionStatus.textContent = `会话清单不可用 · 原因：${label}（${failure.code}）`;
```

两个槽位共用一个句子。实机存储里 `list: null`、`get: {code:"APP_HOST_ERROR"}`，面板却判「会话清单不可用」——清单本身是好的（23 条带标题），用户因此以为功能坏了。这是**把内部诊断字段直接映射成用户文案**的典型错误。

### 修法

严重度分层，而不是取第一个非空：

| 槽位 | 判定 | 呈现 |
|---|---|---|

## 归档下拉与活动归属（控制台 0.5.4）

### 问题一：下拉被归档会话塞满

上一轮为了让空标题的旧会话拿到名字，把清单请求从 `lifecycle: "active"` 改成 `"all"`，同时让归档会话以「已归档·不可钉」的形式进入下拉。实机上 64 条里有 63 条归档，用户展开看到一堵墙——这是把「内部补齐标题」的素材直接当成了「用户可选项」。

修法：`pickableSessionList(entries, activityAt, max = 15)` 只保留 `isPinnableEntry`（真 id 且非 archived），按 `activityAt` 降序、同分按 id 稳定排序，截到 15。面板不再渲染任何归档项，也不加「显示已归档」开关。归档数据留在 `sessionList.sessions` 里，只被 `mergeSnapshot` / 标题回填使用。

同时修掉截断：`projectSessionList` 原来按 sessionId 字母序统一截到 64，会把活跃会话挤掉。现在 active 与 archived 各有预算（128 / 96），active 先入，归档只做补充。

### 问题二：活动仍落到占位符（真因）

`refreshSessionList` 会遍历清单每一条去 `noteResolvedPath`，而 `noteResolvedPath` 是**按插入顺序淘汰的 64 条 LRU**。`lifecycle: "all"` 下清单条数远超 64，于是：

1. 逐条插入，每插入一条就可能淘汰最旧的一条；
2. 遍历结束时表里只剩**最后插入的 64 条**；
3. 活跃会话在清单里通常不是最后 64 条，它的 `path → sessionId` 被挤掉；
4. 事件到达 → `lookupPath` 未命中 → 落到 `unresolved:<hash>` → 真实会话永远空闲。

这与实测完全吻合：`unresolved:aa23721c` working 0 秒、真实会话 2322 秒未动。

修法：

- 容量 512（`RESOLVED_PATH_LIMIT`）；
- **淘汰时先删 `archived` 条目**，active 只有在归档全删完还不够时才动——活跃会话的映射不可能被大归档挤掉；
- 只索引全部 active + 最多 256 条归档（`ARCHIVED_INDEX_LIMIT`），不再无脑灌整份清单；
- 查询先精确命中，再按 basename 兜底（回调路径与清单 `path` 可能有前缀/软链/相对路径差异，会话文件名本身唯一）。

### 解析顺序

```
事件自带 sessionId
  → session:list 的 path → sessionId（宿主确实返回 path，最干净）
  → session:get(sessionId)
  → session:get(sessionPath) → session:get(legacySessionPath) → session:context(sessionPath)
```

最后一条最脆弱：宿主用 `Po()` 解析路径后用 `ug(a, r.agentsDir)` 校验，不在 agents 目录下就 `throw new Error("Invalid session path")`，最终被包成通用 `APP_HOST_ERROR`。所以它降为最后手段，且清单命中时完全不发起。

### 诊断

新增枚举 `pathMatch: "exact" | "basename" | "miss"`、`selector` 增加 `"legacyPath"`，以及四个布尔：`eventHasSessionId`、`listHasPath`、`pathResolvedFromList`、`legacyPathTried`。全部过 `DIAGNOSTIC_FLAGS` / `DIAGNOSTIC_PATH_MATCHES` / `DIAGNOSTIC_SELECTORS` 白名单，值必须是布尔或枚举成员，所以不可能夹带路径、id 或正文。

### 验证

`node --test tests/*.test.mjs` 76 项；`sh tools/run-checks.sh` 全绿；`validate_app` 目录与 archive 均 `errors=0, warnings=1`。关键新增断言：63 归档 + 1 活跃时下拉只剩活跃项；400 条归档不会挤掉活跃会话的映射；清单带 `path` 时**不发生任何 `session:get`** 即可归并；basename 兜底生效；legacy 选择器可独立解出会话；全部失败时占位不抢 `current` 且诊断含布尔、不含路径。

## 宿主事件驱动的表现（控制台 0.5.5）

### 契约

```
PetActivity.hint?: "confirming" | "compacting" | "interrupted" | null
PET_SCHEMA_VERSION = 3, PET_PROTOCOL_VERSION = 3, routes /v3/*
```

除 `hint` 外不新增传输字段。枚举在 `state-core.mjs` 冻结为 `PET_HINTS`，两端 switch 的字符串必须一致。

**一个契约外的必要对齐**：任务书只写了版本号，但原生侧已把路由从 `/v2/*` 改为 `/v3/*`。若不跟随，`probe()` 会 404、`publish()` 永远失败——桥接完全不通。控制台已同步到 `/v3/*`，跨层检查因此从 fail 转绿。这属于"跟随对方已落地的约定"，不是单方面改协议。

### 状态模型

hint 是**展示态**，不是活动态：它不参与 `status`/`running`/`toolName` 的推导，也不进入 `ACTIVITY_EVENTS`（否则会抢走 "最近活动" 的判定）。

```
session_confirmation   → hint=confirming, hintAt=now
confirmation_resolved  → hint=null（仅当当前 hint 就是 confirming）
compaction_start       → hint=compacting, hintAt=now
compaction_end         → hint=null（仅当当前 hint 就是 compacting）
interjection_dropped   → hint=interrupted, hintAt=now
session_closed         → hint=null
```

"只清自己那个 hint"很重要：`confirmation_resolved` 不应抹掉正在显示的 `compacting`。

### 过期

`effectiveHint(session, now)` 在投影期惰性判断：

```
now - hintAt >= HINT_TTL_MS[hint] → null
```

`HINT_TTL_MS` = confirming 600 000、compacting 600 000、interrupted 4 000。缺失或非法 `hintAt` 直接判无效——没有时间戳就无法证明新鲜度，宁可丢掉。惰性计算意味着过期不需要额外定时器，也不会在存储里留下"看起来还没过期"的陈旧值。

### 归属

`handleHintEvent` 走独立入口，与 `resolveIdentity` 分开，因为后者的兜底是**创建占位行**，而展示事件绝不能造出会话：

```
事件自带 sessionId → 用它
否则（仅 confirmation_resolved）→ clearAll: 清掉所有 confirming
否则 path → resolvedPaths / pathIdentities 查真实 id
都查不到 → 丢弃
```

`confirmation_resolved` 的归属被明确标注"不保证存在"（终端提案传 `null`），所以它的缺失不是错误——清掉全部 `confirming` 是唯一诚实的选择：我们知道确认结束了，但不知道是谁的，不能留着过期的提示。

### 隐私

这三个事件的 payload 是整条总线里最敏感的：

| 事件 | 敏感字段 |
|---|---|
| `session_confirmation` | `body`、`title`、`subject.detail`、`payload`（可能含工具参数） |
| `confirmation_resolved` | `value`（用户输入结果）、`sessionId` |
| `compaction_end` | `result`、`errorMessage` |
| `interjection_dropped` | `interjections[].displayText`（用户被丢弃的消息原文） |

实现上只触碰 `event.type` 与归属；`applyHintEvent` 的签名里根本没有 event 之外的取值通道。测试给每个敏感字段塞唯一哨兵，对 `harness.store` 全量与发布 DTO 做 `assertNoSecret`，任一泄漏即失败。

`node --test tests/*.test.mjs` 94 项（新增 `tests/pet-hints.test.mjs` 13 项 + state-core 2 项 + panel 3 项）；`sh tools/run-checks.sh` exit 0；`validate_app` 目录与 archive 均 `errors=0, warnings=1`。

### 两层职责

| 层 | 决定 | 维护者 |
|---|---|---|
| 会话跟随层 | 关注哪条会话、真实在做什么 | `state-core.mjs` 的选择/防乒乓规则（未改） |
| 动作编排层 | 同一语义怎么演 | 新 `PetWorkPoseScheduler` + 既有 `PetPosePlanner`/`PetPoseTimeline` |

### 普通工作节奏

只在「`.working` + 无 hint + 无优先 mood + 窗口可见 + 未开减少动态效果 + 无工具回归宽限 + 无点击回应」时启用：

```
0–6s   thinking        6s
6–10s  busy_left       4s
10–17s thinking 变体   7s
17–22s busy_right      5s
22s 起 从头循环
```

第三阶段按角色取自己的思考变体：Claude → `thinking-2`；DeepSeek 与 deepseek-hoodie → `deepthink`；其余 → `thinking`。`busy_left`/`busy_right` 是通用工作图，不代表工具行为；`reading/writing/searching/running/delegating/drawing` 与 `happy/oops/asking/compact/sleeping/tired/swamped_*/proud` 一律不进普通循环。节奏值集中为 `PetWorkPoseScheduler` 的四个常量，调参只改这四处。

`PetPosePlanner.workPoseSet(characterID:availablePoseNames:)` 负责把候选收敛到该角色 catalog 内：缺 `busy_left/right` 时退到基础 thinking，缺变体时同样退到 thinking，去重后阶段不足两个就返回 `nil`（调度器随之休眠，不建立无效周期唤醒）。

### 工具回归宽限

仅当原生端确实观察到工具姿态、随后**直接从 `.tool` 回到 `.working`** 且无更高优先级时生效：

```
允许结束时刻 = max(工具切入展示时刻 + 2.0, 返回 working 时刻 + 1.2)
```

重复的 working 心跳不延长窗口；新工具、success/error、任一 hint、优先 mood、会话变化、断线都立即打断。因此 `tool → success → working` 不会补播旧工具尾巴，原生从未见过的极短工具也不会被造出来。

### 两套时钟的隔离

- 工作时钟（疲劳 / 忙翻 / 得意）仍只由 `PetPoseMoodTracker` 写。
- 动作时钟只排下一张普通工作图。
- 连续工作段身份 `PetWorkPoseIdentity(sessionId, workSegmentStart)` 的 `workSegmentStart` **直接读 `moodTracker.continuousWorkStart`**（新增只读访问器，指向既有的 `workSince`），调度器不复制、不写入、不自建起点。

三条锁死并有断言：轮换姿态不刷新疲劳阈值；同一会话换角色不重算连续工作时间（只重建展示阶段）；换会话清空阶段与待执行计时，且重置会话相关 mood 计时。

### 身份、代次与旧回调

调度器维护 `identity = (sessionId, workSegmentStart)` 与单调递增 `generation`。任何改变工作上下文的事（会话变、工作段重建、真实工具接管、高优先级抢占与恢复、阶段重建）都让 `generation += 1` 并重建基线；同身份同代次的普通心跳只读不推。计时器回调携带发起时的 `(identity, generation)`，视图侧先比对再允许推进，对不上就只做一次普通重渲染，绝不写姿态、不重排 deadline。时钟统一用 `ProcessInfo.systemUptime`。

### 可见性、减少动态效果与暂停

- 隐藏/不可见/减少动态效果时调度器完全不排自主 deadline，恢复时按当前真实状态重建阶段（不按隐藏时长补算循环）。
- 点击回应期间暂停节奏，恢复时把暂停时长从周期里扣掉，因此不补播被跳过的阶段，也不会让轮换提前取消回应。
- 一次性 wake timer 合并时间线、mood 与调度器三者的最近 deadline；稳定姿态阶段不引入 30/60 Hz 渲染循环。

### 姿态回读

`/v3/state` 字段与版本不变，`pose` 现在是最终实际展示的姿态（含工具宽限与节奏阶段）。主动轮换（含 `busy_left/right`、`deepthink`）不属于缺图替代，不置 `fallback=true`；只有 planner/mood 回退链真的补了替代素材时才置 true。相同姿态心跳不刷新 `since`、不涨 revision。

### 删除的旧陷阱

`PetArtworkPoseMapper`（`PetArtworkCatalog.swift`）把 `.working` 映射成 `thinking`/`writing` 交替、`.tool` 映射成 `busy_left/right` 交替。它没有生产调用点，但正好是「想丰富动作时顺手复用」的陷阱：拿 `writing` 当普通工作装饰直接违例。已删除，`PetCoreTests` 中原先锁着 `working → writing` 的断言换成了「普通工作节奏候选必须落在本角色 catalog 内且不含语义/情绪姿态」。

## 关闭语义修正与固定释放文案（控制台 0.6.3）

本轮只改控制台的会话跟随判定与一处面板文案，不动桌宠、协议、schema、权限与素材。

### 实机证据

用户首次点击「桌宠思考占比过大」固定，界面立刻弹出「已取消固定「桌宠思考占比过大」：会话已关闭」。存储里该会话 `closedAt=18:51:22`、`lastActivityAt=18:58:16`（另两条同型：关闭后 `lastActivityAt` 一直推进）。即宿主发过 `session_closed`，之后同一会话仍在用，但旧实现把 `closedAt` 当成永久的关闭标记。

旧链路：`applyEvent` 写 `closedAt` → 后续活动事件不清零 → `resolveFollow` 只看 `closedAt > 0` → `applyFollowRequest` 刚写入 pin，随后 `refreshFollow` 立即以 `pinned_closed` 释放并落库。

### 新规则

`isClosedSession(record)` = `closedAt > 0 && closedAt >= lastActivityAt`，导出后作为唯一判定入口（`latestActive` / `selectCurrent` / `resolveFollow` 共用）。另有写入层防线：活动事件（`agent_start` / `turn_start` / `auto_retry_start` / `tool_execution_start` / `tool_execution_end` / `agent_end`）把这行的 `closedAt` 清零；`session_created` / `session_forked` 不算活动。`runEnded` 语义未动，关闭后紧接的孤立工具事件仍被既有的 terminal-run 守卫丢弃。

两层同时存在是冗余设计：写入层保证新数据语义正确，判定层让旧存储里「关闭后仍有活动」的记录也不再误判。

### 文案

`released` 是自动释放，不是用户点了取消，所以提示统一改成「已自动解除固定「X」：会话已关闭；现在跟随「Y」。」——首次点击被释放时不再谎称用户取消，真关闭时也仍然读得通。没有改 UI 结构。

- `node --test`：`state-core.test.mjs` 新增 3 项（六个活动事件分别清 `closedAt` 且 pin 存活；旧数据 `closedAt < lastActivityAt` 不释放；真关闭仍 `pinned_closed`，含 idle 事件不清零的断言）；`session-follow.test.mjs` 新增 1 项（关闭→继续活动→点固定，pin 存活、`released` 为 null）。`panel-smoke.mjs` 加断：提示必须是「已自动解除固定」且不得出现「已取消固定」。

## 拖拽拎起两帧动画（桌宠 0.5.7 / 控制台 0.6.4）

本轮给原生桌宠加了一条只有在「真的被拖动」时才出现的两帧往返表现。会话跟随、防乒乓、状态推导、协议 v3、路由、权限与 DTO 结构全部未动；控制台只补了姿态白名单与两处中文文案，布局未改。

### 进入条件（三层闸门）

```
mouseDragged
  → PetDragClickGesture.drag(to:)        跨过 5pt 拖动阈值才给出 translation
  → PetPickUpAnimation.shouldBeginDrag   位置未锁定且 translation 非零
  → 窗口实际 setFrameOrigin             （与移动同一次调用）
```

因此「按下不拖」「单击」「AXPress」「锁定位置」都不会进入；`pointerSequenceActive` 由现有事件策略维护，不受影响。

### 帧节奏

`PetPickUpAnimation` 是纯逻辑：`begin(at:)` 记录首次时刻后**幂等**，重复调用不重置，所以一串 `mouseDragged` 不会把循环钉在首帧；当前帧由单调时钟推导（`frameInterval = 0.16`，A→B→A 一轮 320 ms），没有自己的 timer，只提供 `nextDeadline` 交给既有的单一 one-shot wake timer 合并。

`end()` 立刻退出，渲染随即按**当时最新的真实状态**重算（不是按下前的快照）。取消（`cancelOperation`）、角色切换、会话切换、隐藏/失窗、菜单打开、窗口重挂都调用它，且都会顺带清掉 deadline。

### 不叠影的硬切换

`PetPoseTimeline.update(..., immediate: true)` 是新增参数：拎起帧之间直接落位，不走 0.20 秒交叉淡入（0.16 秒的帧配 0.20 秒淡入必然让两套胳膊同屏）。离开循环后仍恢复普通交叉淡入，真实状态切换的观感没变。

### 覆盖范围与真实性

- 拎起姿态临时覆盖**所有**真实状态的画面：idle、working、mood（含 tired/swamped/proud），以及 **hint（等待确认/压缩/插话）** 和 **error**。定案理由是拖动属于用户自己的直接操作，按住期间由它说话；且它只是显示覆盖——底层会话事件照收，`lastActivityAt`、`workSince`、忙翻窗口、防乒乓计时一律不写，松手立刻回到当时最新的真实状态（包括那些被短暂盖住的提示与报错）。
- 这个判定收敛在 `PetPickUpAnimation.displayPose(realPose:...)` 一处，它刻意不接收 status/hint 参数，因此「拖动时都盖住」不是散落在视图里的分支，也不会被后续改动悄悄变成部分让步。
- 减少动态效果时只显示静态 `picked-up`，不排帧 deadline；拖动本身照常。
- `/v3/state` 回报的就是屏幕上的 `picked-up` / `picked-up-2`，两者都在 catalog 内、不是缺图替代，所以 `fallback` 保持 `false`。

### 命中与窗口接收

`PetWindowEventPolicy.ignoresMouseEvents(pointerIsOnCharacter:duringPickUp:)` 新增 `duringPickUp`：指针序列期间本来就不交还窗口，循环激活时即使光标落在某一帧的透明像素上也继续保持接收，避免帧间轮廓变化导致拖动丢失。绘制、Alpha 命中与位移变换仍是同一套 `PetCharacterMotion` 正逆变换；两帧共用 640 px 画布、同一显示高度与脚线，窗口尺寸不变。
